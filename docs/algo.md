# 算法说明与对比实验（负责人：P4，算法或实验有变动时更新）

## 1. 四项特色功能

| 功能 | 实现 | 参数 | 输出 |
|---|---|---|---|
| 人物最短路 | Cypher `shortestPath`，跳数最少 | from / to | 节点序列 + 跳数 |
| 加权路径 | 最弱环节最强的那条链，`cost` 是该环节的 `weight` | from / to / mode=weighted | 节点序列 + 最弱环节强度 |
| 影响力排序 | GDS PageRank；装不上时退化为度数 | limit | 人物 + 得分 + algorithm |
| 阵营社区发现 | GDS Louvain；装不上时用标签传播 | 无 | 社区编号 + 成员 + 与阵营的一致率 |
| 小世界验证 | 抽样计算平均最短路径与聚类系数，并给出相对随机图的比值 | sample | avg_path / clustering / 两个比值 |

`from` 和 `to` 可以写别名。先按 `Person.name` 精确匹配，没有再查 `aliases`。

## 2. 关键参数与理由

- 最短路搜索上限 `*..6`：和仓库初稿一致。超过 6 跳的路径对页面展示没有意义，也能避免查询失控。
- `weight` 是关系强度，越大越近。一条链有多强，只取决于最弱的那一环，所以加权模式不把强度相加，也不使用 `101 - weight`。GDS 的 Dijkstra 是把边权相加，和这个问题不是一回事，因此加权路径不调用它。
- 强度相同时保留跳数更少的路径。样例里关羽和诸葛亮有一条强度 58 的直接同僚关系，经过刘备的链最弱环节是 95，所以加权结果会经过刘备；跳数结果仍是直接边。
- 社区发现不读取 `faction` 来分组。`agreement` 只是事后拿结果和真实阵营对照。敌对边会把不同阵营连在一起，所以两者不必完全一致。
- 小世界看两个比值：`clustering_ratio = C / C_random`，`path_ratio = L / L_random`。指数是二者相除，大于 1 时 `is_small_world` 为 true。陈述时以比值为主。

## 3. 与关系型数据库的对比实验

测法：同一份 50 人、122 条关系的样例，本机 Docker（Neo4j 5.26.33、MySQL 8.4.13），预热 1 次后取中位数。这不是 P1 的正式数据，小组服务器上的正式库导入后要重跑。

| 查询 | MySQL 写法 | 耗时 | Neo4j 写法 | 耗时 |
|---|---|---|---|---|
| 两跳邻居 | 两次自连接 | 0.74 ms | `*1..2` 且排除直接邻居 | 1.02 ms |
| 最短路，找到即停（刘备→曹操，1 跳） | 逐层查邻居，遇到终点就停 | 0.49 ms | `shortestPath` | 1.05 ms |
| 最短路，找到即停（黄月英→司马懿，2 跳） | 同上 | 0.42 ms | `shortestPath` | 1.37 ms |
| 最短路，全展开（刘备→曹操） | 递归 CTE 展开深度 6 内的简单路径 | 41.24 ms | `shortestPath` | 0.95 ms |
| 度数前十 | `GROUP BY` | 1.00 ms | 按关系计数 | 1.12 ms |

同一问题时，一跳和两跳统计 MySQL 不慢。43 毫秒左右的差距只出现在「把很多路径全部展开」这种写法上，不能当成图数据库本身更快的证据。影响力排名的计时留到正式库再测，因为 GDS 投影的准备时间和查询时间要分开报。

## 4. 局限

- GDS 装不上时，PageRank 退化为度数，社区发现退化为标签传播，`algorithm` 字段会写明。加权路径本来就不用 GDS。
- 样例只有 50 个点。绝对耗时的差距不如写法差别有说服力，答辩时按上表讲。
